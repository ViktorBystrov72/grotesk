# Grotesk

ML медиа сервис который:

- принимает аудио и видео от пользователя
- умеет расшифровывать аудио в текст
- выполняет diarization - разбивает речь по ролям и спикерам
- принимает промпты для редактирования видео по таймкодам или контексту видео
- поддерживает пользовательский и административный контур
- работает через REST API, RabbitMQ и GPU-воркер с Hugging Face моделями.

## Идея сервиса

Сервис будет написан по принципам ООП и даже в какой-то мере по DDD

Пользователь загружает медиафайл.

- Если это аудио, создается задача на транскрибацию и diarization.
- Если это видео, пользователь может прикрепить референс-изображения и задать последовательность команд по таймкодам, например:
  - на 10-й минуте визуально изменить человека
  - на 15-й минуте заменить изображение на фоне на приложенный референс.

## Модели в текущей реализации

- Аудио: openai/whisper-large-v3-turbo
- Speaker diarization: speechbrain/spkrec-ecapa-voxceleb + локальная кластеризация сегментов
- Видео: decart-ai/Lucy-Edit-Dev

## Web-кабинет

Пользователю доступны страницы:

- `/` — главная страница сервиса
- `/register` — регистрация
- `/login` — вход
- `/cabinet` — личный кабинет
- `/cabinet/balance` — баланс и пополнение
- `/cabinet/transcription` — отправка аудио на транскрибацию
- `/cabinet/video-editing` — отправка video-editing запроса

Для HTML-сценария используется cookie-based session auth.

## Bounded Contexts

### 1. identity_access

Отвечает за пользователей, учетные данные и роли.

Основные сущности:

- User
- Credential
- Role

Ответственность:

- регистрация пользователя
- хранение ролей customer и admin
- проверка базового статуса аккаунта.

### 2. billing

Отвечает за баланс, списания и пополнения.

Основные сущности:

- AccountBalance
- BillingTransaction
- TopUpRequest
- CreditReservation

Ответственность:

- пополнение баланса
- резервирование кредитов перед запуском задачи
- подтвержденное списание после успешной обработки
- аудит финансовых операций.

### 3. media_ingestion

Отвечает за загруженные файлы и их метаданные.

Основные сущности:

- MediaAsset
- AttachmentAsset

Ответственность:

- прием аудио, видео и референсов
- определение типа медиа
- базовая валидация формата и статуса файла
- подготовка входных данных для processing.

### 4. catalog

Отвечает за каталог доступных ML-моделей.

Основные сущности:

- ModelProfile
- Capability
- PricingRule

Ответственность:

- описание доступных моделей
- хранение сценариев использования
- указание стоимости и ограничений модели.

### 5. processing

Центральный контекст оркестрации ML-задач.

Основные сущности:

- ProcessingJob
- JobResultRef
- JobHistoryRecord

Ответственность:

- создание задачи
- отслеживание жизненного цикла
- выбор pipeline
- фиксация ссылок на результат
- координация между media, catalog, speech, video_editing и billing.

### 6. speech

Отвечает за результаты обработки аудио.

Основные сущности:

- Transcript
- SpeakerSegment

Ответственность:

- хранение текста расшифровки
- разбиение по спикерам
- хранение временных сегментов и ролей.

### 7. video_editing

Отвечает за команды редактирования видео.

Основные сущности:

- PromptRequest
- TimelineEditOperation
- VideoEditResult

Ответственность:

- хранение пользовательского промпта
- описание операций по таймкодам
- привязка референсов
- фиксация результатов видео-редактирования.

### 8. admin

Отдельный контур для администрирования.

Основные сущности:

- AdminAction
- ModerationDecision

Ответственность:

- ручное подтверждение пополнений
- просмотр транзакций
- аудит административных действий
- расширение под управление каталогом моделей.

## Агрегаты и aggregate roots

Чтобы модель была устойчивой, система строится вокруг нескольких агрегатов.

### User aggregate

Корень агрегата:

- User

Содержит:

- идентификатор пользователя
- учетные данные
- роль
- статус аккаунта.

### AccountBalance aggregate

Корень агрегата:

- AccountBalance

Содержит:

- текущий баланс
- набор транзакций
- информацию о резервировании средств.

### MediaAsset aggregate

Корень агрегата:

- MediaAsset

Содержит:

- тип медиа
- путь к файлу
- статус загрузки
- связанные вложения.

### ProcessingJob aggregate

Главный aggregate root всей предметной области.

Содержит:

- тип задачи
- ссылку на пользователя
- ссылку на входной медиафайл
- ссылку на выбранную модель
- статус выполнения
- ссылку на результат
- сведения о списании кредитов.

### PromptRequest aggregate

Корень агрегата:

- PromptRequest

Содержит:

- исходный промпт
- список операций по таймкодам
- ссылки на вложенные изображения
- бизнес-ограничения для редактирования.

## Основные use cases

### Пользовательский контур

1. Регистрация и вход.
2. Загрузка медиафайла.
3. Загрузка референса к промпту.
4. Создание задачи на транскрибацию аудио.
5. Создание задачи на редактирование видео.
6. Просмотр истории задач и результатов.
7. Просмотр и пополнение баланса.

### Административный контур

1. Просмотр транзакций пользователей.
2. Подтверждение пополнения.
3. Просмотр проблемных задач.
4. Управление доступностью моделей.

## Основные бизнес-правила

- Задача не может быть создана без пользователя.
- Задача не может быть создана без входного MediaAsset.
- Для аудио допустимы только сценарии speech processing.
- Для видео допустимы только сценарии video editing.
- Видео-редактирование может требовать дополнительных вложений.
- У задачи должен быть ровно один тип: transcription или video_editing.
- Баланс пользователя не должен уходить в минус.
- История запросов должна сохраняться независимо от типа задачи.
- Административные действия должны быть аудируемыми.

## Почему это DDD

Проект разделен по слоям:

- domain содержит бизнес-сущности, value objects, интерфейсы репозиториев и доменные сервисы
- application описывает use cases через команды и запросы
- infrastructure будет реализовывать репозитории, UoW, очереди, файловое хранилище и интеграции
- presentation будет содержать REST API, web-контракты и DTO для внешнего мира.

Зависимости направлены внутрь:

- presentation -> application -> domain
- infrastructure -> domain

Доменный слой не знает о FastAPI, ORM, RabbitMQ, Telegram или конкретном способе хранения файлов.

## Пример жизненного цикла аудио-задачи

1. Пользователь загружает аудиофайл.
2. Система создает MediaAsset.
3. Пользователь выбирает транскрибацию.
4. Система создает ProcessingJob типа transcription.
5. Баланс резервирует кредиты.
6. GPU-воркер нормализует аудио, запускает Whisper, вычисляет speaker embeddings через speechbrain/spkrec-ecapa-voxceleb и кластеризует сегменты по спикерам.
7. Результат сохраняется как JSON-артефакт, а история задачи получает ссылку на него.
8. После успеха резерв подтверждается как charge, а задача получает статус completed.
9. При ошибке задача получает статус failed, а резерв снимается с возвратом кредитов.

## Пример жизненного цикла video-editing задачи

1. Пользователь загружает видео.
2. Пользователь прикрепляет референс-изображение.
3. Пользователь задает промпт и список TimelineEditOperation.
4. Система создает ProcessingJob типа video_editing.
5. Баланс резервирует кредиты.
6. GPU-воркер вырезает сегменты по таймкодам, применяет к ним Lucy-Edit-Dev, затем собирает итоговый файл обратно.
7. Результат сохраняется как MP4-артефакт.
8. При успехе резерв подтверждается как charge, а история обновляется.
9. При ошибке резерв снимается и кредиты возвращаются.

## Запуск проекта

Сборка:

```bash
docker compose build
```

Запуск:

```bash
docker compose up
```

После старта можно открыть web-кабинет на `http://localhost/`.

Запуск в фоне:

```bash
docker compose up -d
```

Том hf_cache монтируется в model-preload и worker. Не используйте `docker compose ... down -v`, если не хотите сбросить кэш моделей HF.

Остановка:

```bash
docker compose down
```

Пересборка компонента:

```bash
docker compose build app --no-cache
docker compose up -d app web-proxy
или
docker compose up -d --build app web-proxy
или 
docker compose restart app
```

Пересборка все компонентов:

```bash
docker compose up -d --build
```

Удалить вольюм:

```bash
docker volume rm grotesk_rabbitmq_data
```

## RabbitMQ flow

По умолчанию API публикует processing-задачи в очередь RabbitMQ `ml_tasks`, 
а воркеры читают эту очередь в режиме `one publisher -> many consumers`.

Для запуска нескольких воркеров:

```bash
docker compose up --scale worker=2
```

После этого можно отправить несколько запросов подряд на:

- `POST /predict/transcription`
- `POST /predict/video-editing`

Воркеры дочитывают полный payload задачи из БД, запускают реальный Hugging Face inference и сохраняют артефакты в RESULT_ARTIFACT_ROOT.
В финальной записи истории фиксируются:

- worker_id
- путь к артефакту результата
- метаданные выполненного пайплайна

При completed резерв переводится в charge, при failed создаётся refund и баланс восстанавливается.
